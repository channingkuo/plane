# 项目工作流规则 Spec

- 状态：待评审，尚未实现。
- 开发基线：当前仓库源码，版本声明 `1.5.0`，提交 `618d0eb74658329a6f6e92434ac54231422c5b96`。实施时以当前最新代码为基础，不回退到旧版本。
- 范围：Plane 社区版，按项目配置工作流；首版包含配置页面、后端约束、工作项界面适配及测试。
- 数据前提：尚无在用的历史工作项，不需要历史工作项回填；正常增加数据库迁移。

## 1. 目标与已确认规则

1. 每个项目独立配置创建状态、流转路径、允许操作的项目角色及必填字段。
2. 工作空间管理员维护配置；项目管理员负责 Intake 评审接收及父需求的手动状态修改。两种权限独立判断。
3. 普通创建的是任务，初始状态由配置决定，示例为“待开发”。
4. Intake 列表是待评审需求列表。提交时创建工作项，进入配置的待评审状态；只有项目管理员可接收，接收代表评审通过，同一工作项进入配置的已评审状态。
5. 需求评审通过后拆分子工作项执行开发，需求本身不沿用子任务的开发流程。
6. 所有子工作项完成后，父需求自动进入配置的完成状态；项目管理员也可手动完成，但存在未完成子工作项时必须拒绝。
7. 只有 `Completed` 分组算完成，`Cancelled` 不算。已完成父需求出现未完成子工作项时，自动退回配置的未完成状态。
8. 状态分组由用户手动维护。本功能不自动修改分组。业务约定：“已上线”为最终完成，“完成开发”“测试中”等仍属于 `Started`。
9. 前端提示和后端最终判断使用同一份服务端规则。网页、公开 API、批量操作及后台自动化不能绕过规则。

本节是用户已确认的需求。后续章节中未由用户逐条指定的细节是本 Spec 提出的首版约定，尤其包括：无子项时仅允许管理员确认后手动完成、字段条件按目标状态共用、自动完成因父需求缺字段受阻时不回滚子项完成。这些约定随本 Spec 一起评审，不视为已实现或已单独确认。

## 2. 概念与首版边界

### 2.1 两条业务分支

| 分支 | 来源                          | 业务流程                                        |
| ---- | ----------------------------- | ----------------------------------------------- |
| 需求 | Intake 提交并经项目管理员接收 | 待评审 → 已评审 → 子工作项执行 → 父需求完成     |
| 任务 | 普通创建或需求下拆分          | 配置的任务初始状态 → 配置的开发、测试、上线流程 |

“待评审”“已评审”“待开发”“已上线”均为示例名称；持久化及判断使用同项目状态 ID，不使用名称或展示顺序。

需求和任务共享项目已有状态，但流转规则可以分别指定适用分支，避免任务规则被用于需求。首版不增加第三种业务分支；普通独立任务仍然允许创建。

来源及评审事实由服务端的可信记录确定。已有 `Issue.type` / `IssueType` 可用于类型展示和映射，但标签、客户端传入的类型、`source` 或状态不能单独证明需求来自 Intake 或已通过评审。不以重新添加标签实现需求转换。

### 2.2 首版支持的条件

- 必填字段：负责人、开始日期 `start_date`、截止日期 `target_date`。
- 日期约束：开始日期不得晚于截止日期；按现有字段使用日期粒度，不新增时分秒。
- 流转角色：使用现有项目角色（管理员、成员、访客）；角色勾选不能扩大 Plane 原有的工作项访问和写入权限。
- 父子完成约束和 Intake 接收权限为固定业务规则，不允许通过清空字段规则或角色勾选关闭。

首版不包含任意脚本条件、独立审批引擎、自动分配、通知设计器、可视化流程画布、自定义角色或历史数据迁移工具。

## 3. 权限

| 操作                           | 要求                                                                                   |
| ------------------------------ | -------------------------------------------------------------------------------------- |
| 查看、修改项目工作流配置及启停 | 当前工作空间的有效管理员；可管理该工作空间下项目的工作流，无需同时拥有项目管理员身份   |
| 读取工作项允许操作及失败原因   | 沿用现有工作项读取权限；仅返回执行所需规则，不授予配置编辑权                           |
| 提交 Intake                    | 沿用现有提交权限，不因本功能扩大范围                                                   |
| 接收 Intake / 确认评审通过     | 当前项目的有效项目管理员，同时通过原有资源访问检查                                     |
| 手动修改父需求状态             | 当前项目的有效项目管理员，且满足需求分支的流转和字段规则                               |
| 手动修改任务状态               | 通过原有工作项写入权限，并且项目角色被对应流转允许                                     |
| 自动完成或退回父需求           | 服务端受控的父子聚合操作；无需用户拥有手动修改父需求权限，记录触发操作人及系统执行来源 |

特别约束：

- 工作空间管理员如果在项目中只是成员，不因其工作空间角色获得 Intake 接收或手动修改父需求的权限。
- 项目管理员如果不是工作空间管理员，不能修改工作流配置。
- 项目管理员不享有跳过必填字段或强制完成仍有未完成子项的特权。
- 管理员仍需被普通流转的角色规则明确允许。配置校验保证关键父需求手动完成、重新打开路径对项目管理员可用。
- 状态增删、改名和分组维护沿用现有权限；但不得删除正在被有效工作流引用的状态，或把引用状态改为与配置约束不兼容的分组。

## 4. 配置页面

### 4.1 入口与配置项

入口位于项目设置中的“工作流”。完整编辑页面仅工作空间管理员可访问。

| 配置项             | 说明                                                                                                                 |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- |
| 启用工作流         | 关闭时保留配置；启用前必须通过完整校验                                                                               |
| 普通任务初始状态   | 普通新建、快捷新建、子任务创建、草稿发布所使用的状态                                                                 |
| Intake 提交状态    | 待评审需求提交后使用的状态                                                                                           |
| Intake 接收状态    | 评审通过后父需求使用的状态                                                                                           |
| 父需求完成状态     | 子工作项全部完成后使用的状态；必须属于 `Completed`                                                                   |
| 父需求自动退回状态 | 已完成父需求出现未完成子工作项时使用的状态；必须为非 `Completed`、非 `Cancelled`、非 `Triage` 状态；可与接收状态相同 |
| 流转规则           | 适用需求/任务、原状态、目标状态、允许的项目角色                                                                      |
| 状态必填字段       | 适用需求/任务、目标状态、负责人/开始日期/截止日期                                                                    |

状态必填字段与流转规则放在同一页面管理：字段条件属于目标状态，各进入路径共享，避免同一状态因入口不同产生不同完整性要求。页面展示某条流转时，同时展示其目标状态的字段要求。

页面提供“需求”“任务”两个规则视图，以列表或矩阵编辑，不要求图形流程画布。展示 Intake 提交、接收及父子自动聚合的固定特殊路径，说明其权限与条件；它们不由普通角色勾选覆盖。

### 4.2 保存、启用与变更校验

- 所有引用状态必须存在、未删除并属于当前项目。
- Intake 提交、接收状态必须不同；提交、接收、任务初始状态均不能属于 `Completed` 或 `Cancelled`；接收状态不能属于 `Triage`。
- 普通任务初始状态不得属于 `Triage`。工作流不能直接创建已完成任务。
- 父需求完成状态必须属于 `Completed`；退回状态必须符合上表约束。
- 不允许重复的同分支、同原状态、同目标状态规则；普通流转必须至少允许一个角色。没有规则表示拒绝流转。
- 支持相同状态的普通字段修改，不视为一次流转，但仍验证该状态的字段要求。
- 角色限定为项目现有角色。所有自定义规则与原有权限取交集。
- 配置必须包含父需求从接收/退回状态手动到完成状态，以及从完成到退回状态的路径，并允许项目管理员。
- 父需求自动完成和自动退回是独立系统路径；配置必须展示并校验其端点及字段要求，不依赖伪造项目管理员身份执行。
- 配置启用后，普通工作项接口不得把工作项送入 Intake 待评审入口，或伪造 Intake 接收。
- 涉及完成判定的状态分组变更，也必须触发工作流配置校验和受影响父需求重新计算。
- 保存时使用配置版本，拒绝覆盖另一管理员刚保存的版本，并提示刷新。
- 启用或修改规则前，检查现有受控工作项是否满足新约束，以及自动完成/退回目标是否有可用路径。存在不兼容时返回具体问题；不得静默改写工作项。
- 保存及启停记录审计。执行请求以事务中读取的有效配置版本为准。

首次使用时不自动创建或重分组用户状态；页面引导管理员选择已有状态，配置完整后才能启用。

## 5. 创建与 Intake

### 5.1 普通任务创建

- 所有普通任务创建入口使用配置的任务初始状态，不能通过请求指定“开发中”或“已上线”等其他初始状态绕过流程。
- 页面预填并锁定初始状态。API 若显式提交冲突状态，返回错误并说明项目初始状态要求，不静默接受冲突参数。
- 新建时同样验证初始状态的字段要求；不满足则不创建。
- 创建时不能指定为已评审需求，不能伪造来源、评审人或接收记录。
- 需求下的新建子工作项必须属于同项目，父需求必须已经真实接收通过；子工作项仍使用任务初始状态。
- 首版允许普通独立任务；不强制每个任务都关联需求。

### 5.2 Intake 提交

- 创建一条工作项及其 Intake 关联，使用配置的提交状态，标记待评审。
- 待评审条目在 Intake 列表展示，不因配置状态不是原生 `Triage` 分组而意外出现在普通任务列表、看板和完成统计中。
- 提交后不能通过普通工作项状态更新、类型更新、解除关联等方式进入正式需求流程。
- 已提交者在原有权限范围内可编辑标题、描述等内容；不能自行接收。
- 待评审、拒绝、稍后处理、重复等 Intake 业务状态继续与工作项进度状态区分，不使用进度状态代替接收事实。

### 5.3 Intake 接收即评审通过

仅项目管理员可执行。一个事务内完成以下动作：

1. 锁定 Intake 记录和关联工作项，验证真实来源、有效角色及当前接收资格。
2. 校验配置的接收状态和字段条件。
3. 将 Intake 标记为已接收；将同一工作项移到接收状态。
4. 记录评审通过、评审人、评审时间及配置版本。
5. 提交后展示为已评审父需求，并开放拆分子工作项。

不创建第二条需求；失败时上述变更全部回滚。重复接收不得重复创建记录、重复发送活动，或把已经推进的需求重置到接收状态。已接收条目不得通过普通 Intake 更新清除其历史接收事实；重新评审不在首版范围内。

## 6. 状态流转与字段验证

每次创建或更新，服务端按以下次序处理：

1. 检查原有资源权限及当前项目工作流是否启用。
2. 在事务中读取并锁定工作项，读取有效配置和项目角色。
3. 根据可信来源确定需求/任务分支，读取真实原状态。
4. 合并已保存值与本次变更，构造提交后的最终数据；区分字段未提供和显式清空。
5. 若状态变化，验证该分支是否允许此流转，当前角色是否允许。
6. 验证目标状态必填字段、负责人有效性和日期顺序；父需求完成时额外验证子工作项。
7. 原子保存工作项、多对多负责人关系、来源/评审记录及审计事件，并处理必要的父需求聚合。
8. 数据库提交后再派发异步活动、通知及其他外部副作用。

行为示例：

- 一次请求补齐负责人及起止日期，同时从待开发进入开发中：满足角色和流转条件时成功。
- 只改状态，缺少截止日期：拒绝，指出缺少截止日期。
- 仍处于开发中但清空负责人：拒绝，原负责人及状态保持不变。
- 只修改截止日期，导致截止日期早于已保存的开始日期：拒绝。
- 两个请求并发改同一工作项：串行依据锁内最新状态判断，不能都按旧状态通过校验。
- 非状态更新也验证当前状态的必填条件；管理员不例外。

状态名称变化不改变规则；引用状态的删除和分组变化受配置完整性约束。工作流仅约束应用支持的写入路径，不承诺阻止具有数据库写权限的人直接修改数据。

## 7. 父需求自动完成与重新打开

### 7.1 完成判定

- 父需求必须来自已经接收的 Intake，并且尚未取消。
- 子工作项范围为父需求下所有未软删除的直接子项及后代子项；归档的子项仍参与判断，归档不等于完成。多层关系不能只检查第一层状态。
- 子工作项的状态分组为 `Completed` 才算完成；`Started`、`Cancelled`、无状态等均未完成。
- 首版按已有父子关系逐层计算，不另建关系树；不允许循环或跨项目父子关系。
- 至少有一个子工作项且全部完成，才触发父需求自动完成。没有子工作项不会刚接收就自动完成。
- 对有多层子工作项的任务，只有其后代均完成才允许该任务进入 `Completed`，防止把未完成的孙工作项藏在已完成子任务下。
- 本功能自动完成和退回的对象是 Intake 父需求，不扩展成通用任务树自动流转。嵌套子项重新打开时，重新计算其所属父需求；中间层任务即使仍显示完成，也不能使未完成后代被排除在父需求的判断之外。

### 7.2 自动完成

最后一个未完成子工作项完成后，父需求自动进入配置的完成状态。该操作使用显式系统路径，仍验证目标状态字段和子项完成条件。

如果父需求自身缺少完成状态所需字段，子工作项可以正常完成；父需求保持原状态，显示“子工作项已全部完成，但父需求缺少……”，记录受阻原因。补齐父需求字段后再次计算并完成，不依赖用户重复修改子任务。

已经完成或取消的父需求不重复写入完成活动；取消的父需求不因子任务完成而自动恢复。恢复已取消需求必须由项目管理员通过配置允许的路径进行。

### 7.3 项目管理员手动修改

- 只有项目管理员可手动修改父需求状态，并遵守需求分支规则及目标状态字段条件。
- 选择任意 `Completed` 分组目标状态时，必须检查全部子工作项；存在未完成项则阻止提交。
- 提示：“还有 N 个子工作项未完成，不能完成该工作项。”提供可访问的未完成项列表；不能提供强制完成按钮。
- 没有子工作项时，项目管理员可手动完成，提交前提示“该需求尚无子工作项，确认直接完成？”。这是首版明确的空子项行为；自动完成仍要求至少一个子项。
- 项目管理员可以通过配置允许的路径手动重新打开父需求。手动重新打开后，不因一次无关字段更新立即被自动完成覆盖；下一次子项完成情况或关联关系变化才重新计算自动完成。

### 7.4 已完成需求出现未完成子项

以下操作必须在同一业务事务内重新检查父需求：

- 将已完成子工作项重新打开或改为已取消。
- 在已完成父需求下新增未完成子工作项。
- 把未完成子工作项关联到已完成父需求。
- 子工作项状态分组或父子关联变化导致聚合结果改变。

存在未完成子工作项时，允许有权限的用户执行原操作，同时将父需求自动退回配置的未完成状态。操作人无需额外拥有父需求手动修改权限；审计必须说明其原操作触发了父需求自动退回。

如果退回目标已失效或其字段条件不满足，整个原操作必须失败并提示原因，不能留下“父需求已完成、子工作项未完成”的不一致状态。

重新关联和删除子项时，重新计算涉及的旧父需求、新父需求；删除后无子项不触发自动完成。多项并发完成、重新打开或改父项时，按统一顺序锁定关联工作项，避免错误聚合、重复完成和死锁。

## 8. 接口和数据设计约束

以下为建议接口契约，具体 URL 命名遵循仓库现有规范。

| 接口用途                         | 关键行为                                                 |
| -------------------------------- | -------------------------------------------------------- |
| 读取/保存项目工作流配置          | 保存整份有效配置及版本；仅工作空间管理员                 |
| 验证配置是否可启用               | 返回配置错误和受影响工作项，不修改数据                   |
| 查询工作项可执行流转             | 返回目标状态、是否有权限、缺少字段、阻止原因及配置版本   |
| 预检合并后的变更                 | 可携带拟填写字段，仅返回预检结果；不保存、不视为执行授权 |
| 现有创建、更新及 Intake 接收接口 | 保持主要入口，统一调用后端工作流服务                     |

最小数据职责：

- `ProjectWorkflow`：项目、启用状态、配置版本、五个状态引用及修改人。
- `WorkflowTransition`：项目、需求/任务分支、原状态、目标状态、允许项目角色。
- `WorkflowStateRequirement`：项目、分支、状态、必填字段集合。
- 可信来源与评审记录：工作项、创建来源、真实 Intake 关联、接收人、接收时间；不可通过普通工作项输入覆盖。Intake 关联被删除也不能抹去已发生的接收审计。
- 流转及配置审计：工作项/项目、原状态、目标状态、用户或系统来源、触发人、配置版本、时间及受阻原因。可复用现有活动日志，但不能仅依赖异步日志作为评审事实。

普通用户更改工作项类型或标签不能重置来源、取消规则或把任务变成已评审需求。受控任务在项目间移动时必须重新验证目标配置，首版未接入的移动/导入路径明确拒绝，不能静默绕过。

建议错误结构：

```json
{
  "code": "WORKFLOW_REQUIRED_FIELDS_MISSING",
  "message": "请先填写负责人和截止日期",
  "details": {
    "fields": ["assignees", "target_date"],
    "from_state_id": "uuid",
    "to_state_id": "uuid",
    "workflow_revision": 3
  }
}
```

- `400`：非法流转、字段不完整、子项未完成、来源不合法、配置错误。
- `403`：没有资源权限、项目角色不允许、非项目管理员接收、非工作空间管理员改配置。
- `409`：配置版本冲突或显式并发版本冲突，提示刷新后重试。
- 字段命名及响应兼容现有 API；内部 Web API 的 `assignee_ids` 与公开 API 的 `assignees` 统一映射到相同业务校验。

## 9. 前端行为

- 普通任务新建时锁定项目配置的初始状态，并提示所需字段；在其他状态列快捷创建也不改变此规则。
- Intake 接收按钮仅项目管理员可见；后端独立验证，按钮隐藏不是权限边界。
- 已评审需求提供拆分子工作项入口，显示执行进度、自动完成目标及阻止完成的子项。
- 状态选项区分“没有允许路径/角色无权限”和“路径允许但字段未填”；后者展示缺少字段，并允许在同一提交中补齐。
- 看板拖拽、列表行、详情页、批量操作和快捷操作采用相同规则语义。
- 乐观更新失败时恢复状态、卡片位置及计数，显示服务端实际原因。
- 子项操作导致父需求自动完成或退回后，同步刷新父需求状态和列表统计。
- 项目管理员尝试完成仍有未完成子项的父需求时，显示阻止提示及子项入口，不允许忽略提示提交。
- 配置及错误文案使用现有国际化机制；界面显示业务术语，不向用户暴露实现细节。

## 10. 后端覆盖范围

统一规则服务需要覆盖并验证：

1. 内部 Web API 工作项创建、更新。
2. 公开 REST API 创建、更新及 Intake。
3. Intake 提交、接收及相关嵌套工作项更新；公开 Space 提交入口。
4. 草稿发布、快捷创建、子任务创建、父子关系调整。
5. 批量状态/日期更新、复制及导入等实际存在的写入入口。
6. 自动关闭等直接调用 ORM `update` / `bulk_update` 的后台路径。
7. 影响完成判定的状态分组变更、删除和项目间移动。

不得只依赖单个 Serializer、`Model.save()` 或信号；直接批量更新必须显式接入服务。原有自动关闭功能在受控项目中也遵守普通任务规则，不设置万能绕过标志；与规则冲突时跳过该项并记录原因。父子聚合仅使用其专用系统路径。

批量操作先验证全部对象，再在同一事务提交；有任一项失败则全部回滚，并返回对应工作项原因。未接入规则的入口在启用项目中应明确拒绝。关闭工作流的项目保持原有行为，但不能清除来源和审计记录；重新启用必须重新校验配置和工作项。

## 11. 验收用例

| 编号  | 场景                                                         | 预期                                                           |
| ----- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| AC-01 | 工作空间管理员保存项目配置                                   | 成功，只影响该项目                                             |
| AC-02 | 项目管理员但非工作空间管理员保存配置                         | 403                                                            |
| AC-03 | 工作空间管理员在项目中仅为成员，尝试接收 Intake              | 403                                                            |
| AC-04 | 项目管理员接收 Intake                                        | 原工作项进入接收状态，记录评审，无重复工作项                   |
| AC-05 | 重复接收同一条目                                             | 无重复评审/活动，不重置已有需求状态                            |
| AC-06 | 普通创建、看板快捷创建、API、草稿发布                        | 均遵守任务初始状态；显式冲突状态被拒绝                         |
| AC-07 | Intake 提交                                                  | 使用提交状态，仅按待评审条目展示，无正式需求执行权限           |
| AC-08 | 普通接口伪造来源、评审或需求类型                             | 不能绕过 Intake 接收                                           |
| AC-09 | 待评审需求下创建执行子任务                                   | 拒绝；真实接收后允许                                           |
| AC-10 | 直接跨过没有配置的流转                                       | UI、API、拖拽均拒绝                                            |
| AC-11 | 配置未授权的项目角色流转                                     | 403；管理员无隐含豁免                                          |
| AC-12 | 同一请求补齐负责人、起止日期并开始开发                       | 成功                                                           |
| AC-13 | 缺字段、显式清空、日期与已有值冲突                           | 拒绝，工作项和负责人关系不被部分修改                           |
| AC-14 | 最后一个子项进入 Completed                                   | 父需求自动完成，只有一条完成活动                               |
| AC-15 | 某子项为 Cancelled 或 Started                                | 父需求不自动完成；手动完成被阻止                               |
| AC-16 | 项目管理员尝试完成有未完成子项的需求                         | 提示未完成数量和列表，无强制完成入口                           |
| AC-17 | 没有子项的已评审需求                                         | 不自动完成；项目管理员可经确认手动完成                         |
| AC-18 | 完成父需求下重新打开子项/新增未完成子项                      | 操作和父需求自动退回一起成功；无父项手动权限也可受控触发       |
| AC-19 | 自动退回目标条件不满足                                       | 原子项操作整体失败，不留下父子状态不一致                       |
| AC-20 | 父需求缺少自动完成所需字段                                   | 子项可完成，父项显示受阻原因；补齐后自动完成                   |
| AC-21 | 子任务尝试完成但还有未完成后代；或已完成任务的后代被重新打开 | 前者拒绝任务完成；后者重新计算并退回父需求，不能隐藏未完成后代 |
| AC-22 | 并发完成/重新打开/调整父项                                   | 无错误完成、丢失更新和重复活动；相关父需求均正确               |
| AC-23 | 批量更新有一项不合法                                         | 全部回滚，返回逐项错误                                         |
| AC-24 | 自动关闭、公开 API 或导入尝试绕过                            | 按规则执行或明确拒绝；不静默写入                               |
| AC-25 | 状态改名/删除/变更分组                                       | 改名不影响绑定；非法删除/分组变化被阻止；合法分组变化重新聚合  |
| AC-26 | 归档/删除/重新关联子项                                       | 按定义重算，归档不冒充完成，空子项不触发自动完成               |
| AC-27 | 前端乐观更新被后端拒绝                                       | 状态、位置、计数恢复，显示准确原因                             |
| AC-28 | 两个管理员同时编辑配置                                       | 后保存的旧版本收到 409，不能覆盖新配置                         |
| AC-29 | 工作流未启用的其他项目                                       | 原行为不受影响                                                 |
| AC-30 | 项目管理员手动重新打开父需求，所有子项仍完成                 | 无关字段更新不立即撤销手动操作；子项完成情况/关联变化后再聚合  |

测试分层：规则服务单元测试、数据库/事务与权限接口测试、公开与内部 API 合约测试、前端组件测试、真实浏览器端到端测试。并发和父子聚合必须使用真实 PostgreSQL 验证，不以 Mock 替代。
