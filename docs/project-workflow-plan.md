## 1. 目标与交付原则

在当前分支完成“项目配置 → 后端执行 → 工作项操作 → 父子聚合 → 审计和验收”的完整功能。配置页面属于首版，不延期到后续版本。

首版仅支持需求和任务两条业务分支、现有项目角色、负责人和起止日期条件。Intake 待评审是来源生命周期，不新增第三条开发流程。沿用已有状态及其分组，不自动创建、重命名或重分组用户状态。

工作空间管理员维护配置；项目管理员接收 Intake 和手动修改父需求。角色规则与原有资源权限取交集，管理员没有绕过字段、路径或父子约束的特权。父需求自动完成和退回使用各自专用的系统操作，不提供通用跳过校验参数。

各阶段同时交付对应测试。未覆盖全部写入路径及父子聚合前，只允许在独立开发/测试环境启用配置，不把阶段性能力当作可发布功能。

## 3. 拟议实现结构

本节命名与字段为实施建议，不表示现有代码已具备这些模型或接口。P0 固定契约，后续变动需同步更新本计划、类型及测试。

### 3.1 数据结构与约束

| 拟议模型/记录 | 最小职责 | 关键约束 |
| --- | --- | --- |
| `ProjectWorkflow` | 每项目一份配置，启用状态、版本、五个特殊状态引用和修改人 | 仅绑定同项目有效状态；启用必须完整校验；配置版本用于并发保存 |
| `WorkflowTransition` | 需求/任务分支、原状态、目标状态、允许项目角色集合 | 有效配置内分支和状态对唯一，角色非空；没有路径即拒绝 |
| `WorkflowStateRequirement` | 分支、目标状态、必填字段集合 | 同分支目标状态唯一；仅接受负责人、开始日期、截止日期三个字段 |
| `IssueWorkflowContext` | 一对一保存可信创建来源、Intake 来源标识、接收人和接收时间、接收配置版本 | 只由服务端操作写入；保留原始 Intake 标识快照，解除或删除关联不抹去接收事实 |
| 父需求聚合运行信息 | 子项变化版本、手动重新打开时的版本、自动完成受阻原因 | 与父需求上下文一起持久化；支持字段补齐重试，并避免无关更新撤销手动重新打开 |
| 工作流审计记录 | 配置保存/启停、流转、评审、系统聚合、触发人、有效配置版本及原因 | 成功记录与业务写入同事务；评审事实不能只存在于异步活动日志中 |

- 为项目、工作项、分支/状态对及父子查询增加必要唯一约束和索引；具体迁移编号依据实施时迁移图生成。
- Intake 来源与接收事实不由 `Issue.type`、标签、客户端 `source` 或进度状态推导。普通类型更新不能改变上下文。
- 新建任务和 Intake 时均记录可信来源；未启用项目保持原操作行为，同时保留后续可验证的来源/接收记录。
- 按 Spec 前提不回填历史工作项。启用前发现缺少可信记录或不兼容工作项时，返回具体问题，不猜测其评审事实，也不静默修复。
- 使用新增迁移，不改写已合并迁移。状态引用删除、软删除与配置校验联动，不能留下启用但引用失效的配置。

### 3.2 服务层与统一数据

建议在 `apps/api/plane/services/workflow/` 新建模块，将以下职责分开：

| 模块职责 | 输入与输出 |
| --- | --- |
| 配置和权限 | 校验配置完整性、角色身份、版本及现有数据兼容性，保存整份配置 |
| 补丁归一化 | 将 Web/API/Intake 字段映射成统一结构，保留“未提供”和“显式清空”的区别 |
| 规则评估 | 根据可信分支、真实原状态、最终数据和实际角色返回允许目标、缺字段和阻止原因 |
| 写入编排 | 创建、修改、接收、关联、批量操作的事务边界与审计，调用原有必要持久化逻辑 |
| 父子聚合 | 查询全部未软删除后代，完成/退回父需求，处理受阻和手动重新打开 |
| 查询投影 | 为配置页、普通新建及工作项操作提供最小规则摘要，不泄漏完整配置编辑能力 |

预检和实际执行使用相同评估器。预检结果不是执行授权；执行时重新读取锁内状态、角色和有效配置。Serializer 保留基础类型及原有资源校验，但不能先保存再调用规则服务。

所有写入先验证合并后的工作项字段和负责人集合，再原子保存工作项、M2M、来源、评审及审计；字段校验失败不能留下部分关系更新。状态相关写入同步维护 `completed_at`，包括批量及聚合路径。

### 3.3 事务与并发约定

首版优先选择容易证明正确的锁策略：

1. 进入业务事务后，先按项目 ID 固定顺序锁定涉及的 `Project` 行，再读取启用状态及配置版本。配置新增、启停、状态维护和所有受影响写入遵守相同顺序。
2. 即使尚无配置或工作流未启用，也在检查启用状态前经过同一锁入口，避免启用检查与旧写入并发穿透。锁的引入不改变未启用项目的业务规则。
3. 同项目写入在首版串行；随后按工作项 ID 固定顺序锁定对象、父链及 Intake 记录。获取项目锁前不能先锁子项，防止不同入口锁顺序相反。
4. 父子范围、循环、跨项目约束及最终完成状态在锁内重新读取。项目锁同时约束新建和重新关联，避免只锁已有子项而漏掉并发新增。
5. 批量操作先验证全部对象及聚合结果，再统一写入。一个失败则整个事务回滚，返回对应工作项原因。
6. 提交成功后通过 `transaction.on_commit` 派发活动和通知；同步审计是评审及聚合事实来源。整体失败用错误响应及结构化日志记录，不提交半成业务数据。

该策略会增加同项目写入等待。P4 以并发测试和查询/锁等待数据评估成本；未来优化为更细锁时必须保留同等正确性，不能直接去掉项目锁。

### 3.4 父需求聚合与触发规则

- 在锁内沿现有父子关系收集全部未软删除后代；归档仍计入，只有 `completed` 分组算完成。检测循环和跨项目关系，不能使用会排除归档项的默认业务列表查询。
- 完成任何带后代的任务前检查全部后代。自动流转仅作用于已接收、未取消的 Intake 父需求；中间任务不会自动变成完成或退回。
- 子项状态/分组、创建、删除、恢复及关联变化触发受影响父需求重新计算；重新关联同时计算旧、新父链。将恢复列为实施时需核对的实际入口。
- 子项全部完成且至少一个时尝试自动完成。父需求缺少完成字段，则成功保存子项，持久化父需求受阻原因；补齐相应字段后重试聚合。
- 父需求已完成而出现未完成后代时，子项操作与父需求自动退回必须同事务成功；退回目标或字段失效则整体拒绝。
- 手动重新打开记录当前子项变化版本。相同版本下的无关字段更新不触发自动完成；下一次真实子项完成情况或关系变化才重新计算。字段补齐重试仅针对已有自动完成受阻原因。
- 重复接收、重复请求和并发最后子项完成不得重复写评审或完成活动；空子项不自动完成。管理员手动完成空需求按 Spec 提示确认。

### 3.5 接口契约

内部接口建议沿用 `/api/workspaces/{slug}/projects/{project_id}/` 前缀；公开 API 保持已有前缀和认证方式，通过适配器调用同一服务。

| 用途 | 建议接口或接入方式 | 权限和返回约定 |
| --- | --- | --- |
| 读取/保存完整配置 | `GET/PUT workflow/` | 仅有效工作空间管理员；携带配置版本，保存成功返回新版本 |
| 配置预检 | `POST workflow/validate/` | 同配置权限；返回配置错误、受影响项及自动目标可用性，不修改数据 |
| 普通创建所需规则 | 新建上下文中增加最小摘要 | 沿用原有创建权限；仅返回启用状态、初始状态及字段要求 |
| 工作项允许操作 | `GET issues/{issue_id}/workflow/` | 沿用资源读取权限；返回业务分支、配置版本、目标状态、权限/字段阻止原因及聚合受阻摘要 |
| 变更预检 | `POST issues/{issue_id}/workflow/preview/` | 校验资源访问和拟执行动作；接受补丁，允许一次补齐字段，不保存数据 |
| 实际写入 | 现有创建、修改、草稿发布、Intake 接收及批量接口 | 后端独立执行规则；不另设绕过原接口的写入通道 |

- 使用 Spec 错误结构及 `400/403/409` 语义。错误字段名称与调用端现有命名保持兼容，共享类型声明内部映射。
- 未完成子项返回总数及调用者可访问的列表；不得借错误或预检泄漏无读取权限的工作项内容。
- 列表、看板与详情使用相同语义；批量获取摘要或利用现有批量加载，避免每个卡片新增一次请求。
- 配置、项目角色、状态或工作项变化后使相关缓存失效。前端携带版本用于提示刷新，不能因客户端版本相同而省略服务端再校验。

## 7. 验证命令与发布检查

以下是实施时应执行的命令，不是本次计划编写已经执行的测试。命令均从仓库根目录运行，除非另有说明；新增测试脚本在 P0 落地后再固定最终调用方式。

### 7.1 后端

按 `apps/api/tests/RUNNING_TESTS.md` 准备隔离测试栈；配置文件尚未生成时先运行 `./setup.sh`，存在已有配置时避免覆盖。

```bash
# 运行已有和新增 unit/contract 用例，pytest 标记沿用仓库声明
docker compose -f docker-compose-test.yml run --rm --build api-tests pytest -m "unit or contract"

# 完整后端回归，包含真实 PostgreSQL 并发用例
docker compose -f docker-compose-test.yml up --build --abort-on-container-exit --exit-code-from api-tests

# 在测试容器内验证模型/迁移漂移
docker compose -f docker-compose-test.yml run --rm api-tests python manage.py check
docker compose -f docker-compose-test.yml run --rm api-tests python manage.py makemigrations --check --dry-run

# 清理本项目独立测试资源
docker compose -f docker-compose-test.yml down -v
```

迁移另设验证步骤：默认 pytest 的 `--nomigrations` 不能证明迁移可运行。在独立空库执行 `migrate`；另在基线数据库上执行升级，验证约束、来源表、审计表和配置默认关闭。参考 `.github/workflows/migration-check.yml` 检查迁移图；该工作流当前目标分支不含本功能分支，不能假定推送后自动覆盖，需明确本地/CI 执行证据。

并发用例使用 `pytest.mark.django_db(transaction=True)` 或等价真实事务配置、独立连接和显式同步点；使用现有 `unit/contract/slow` 等标记，不引入未注册标记。Mock 仅替代通知等外部副作用，不替代数据库锁和聚合查询。
